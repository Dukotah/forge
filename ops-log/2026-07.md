A ~950-word guide targeting the queries **"X-Frame-Options vs frame-ancestors"**, **"do I still need X-Frame-Options"**, **"X-Frame-Options deprecated"**, and **"CSP frame-ancestors clickjacking"** — a developer whose security scanner (HardenCheck or any other) flagged both a missing X-Frame-Options header and a CSP without a `frame-ancestors` directive, and who doesn't understand the relationship between them.

**Article structure (all content is genuine, technically accurate):**
- What the confusion is — scanners flag both XFO and frame-ancestors absence; they protect against the same attack (clickjacking), so the reader naturally wonders which they actually need to set
- What X-Frame-Options does — `DENY` / `SAMEORIGIN` / `ALLOW-FROM` table; key callout: `ALLOW-FROM` is dead (Chrome/Edge/Safari never supported it; Firefox dropped it in 2019); only two useful values remain
- What CSP `frame-ancestors` does — syntax for `'none'`, `'self'`, specific origins, wildcards; covers `<embed>` and `<object>` which XFO doesn't; callout: frame-ancestors only works in HTTP response headers, not in meta tags (a common misconception)
- Key differences table — 7 dimensions: browser support, block all, allow same-origin, allow third-party, wildcard support, embed/object coverage, meta tag delivery
- Precedence rules — what browsers actually do when both headers are present: modern browsers (Chrome/Firefox/Edge/Safari) use `frame-ancestors` and ignore XFO; IE ignores CSP entirely and uses XFO. Browser-by-browser precedence table.
- The practical recommendation — set BOTH; belt-and-suspenders; no conflict; covers IE 9+ through Chrome latest. Three scenario examples: no embedding, same-origin embedding, trusted partner embedding (with IE caveat)
- Tip callout: if you have no CSP yet, `X-Frame-Options: DENY` is a one-liner you can ship today while building out a full CSP
- Per-platform deployment snippets showing BOTH headers together: nginx, Apache (.htaccess), Vercel (vercel.json), Next.js (next.config.js), Netlify (_headers), Cloudflare Pages (_headers)
- GitHub Pages callout (no custom response headers on plain GitHub Pages; Cloudflare Transform Rule workaround)
- Verify with HardenCheck CTA — clarifies that HardenCheck reads both XFO and frame-ancestors inside CSP; passing CSP frame-ancestors is sufficient even without XFO
- FAQ + FAQ JSON-LD schema (6 questions): does XFO still work; ALLOW-FROM; what frame-ancestors covers that XFO doesn't; should you set both; does HardenCheck check both; does meta tag CSP cover frame-ancestors

### Why this batch

Third guide in HardenCheck's rotation. "X-Frame-Options vs frame-ancestors" is one of the most searched clarification queries for developers running security scanners — the confusion comes from two separate scanner warnings pointing at the same underlying threat. Most existing articles on this topic either explain each header in isolation or give a terse "use frame-ancestors" recommendation without explaining the precedence rules, the ALLOW-FROM graveyard, or the IE fallback rationale. This guide covers all three: the belt-and-suspenders recommendation (set both), the precise browser precedence table (who wins when both are present), and the practical `ALLOW-FROM` warning (it's dead; stop trying to use it). The meta tag callout for `frame-ancestors` is the most commonly missed gotcha — developers who can't set response headers often try a meta tag workaround, which silently fails. The GitHub Pages callout directly addresses the constraint many Copper Bay Labs users face (static sites on GitHub Pages).
