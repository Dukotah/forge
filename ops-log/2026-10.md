Keyboard inaccessibility maps to four WCAG success criteria frequently cited in lawsuits: 2.1.1 Keyboard (Level A), 2.1.2 No Keyboard Trap (Level A), 2.4.3 Focus Order (Level A), and 2.4.7 Focus Visible (Level AA). The query cluster ("how to test keyboard navigation accessibility", "keyboard accessibility testing", "test tab order website", "wcag 2.1.1 keyboard test", "focus order accessibility") is high-intent — searchers are developers either responding to a demand letter or proactively auditing their site.

### Guide content summary

**JSON-LD:** TechArticle with nested FAQPage (7 Q&As), datePublished/dateModified 2026-10-13

**Sections:**

1. **WCAG criteria** — 4-card grid: 2.1.1 Keyboard (Level A), 2.1.2 No Keyboard Trap (Level A), 2.4.3 Focus Order (Level A), 2.4.7 Focus Visible (Level AA). Callout about WCAG 2.2's new 2.4.11 Focus Appearance requirement.

2. **Keyboard testing protocol** — full table: Tab, Shift+Tab, Enter, Space, Arrow keys, Escape, Home/End — what each key does and what you're checking for. Callout: start every test with a hard reload; skip nav link should be the first Tab stop.

3. **5 things to check** — numbered list: (1) Is the focused element always visible? Checks for `outline:none` CSS resets. (2) Is the focus order logical? Flags CSS reordering (absolute positioning, flexbox `order`). (3) Can you reach every interactive element? Hover-only menus, elements not in tab order. (4) Can you escape every component you enter? Focus traps in maps, iframes, modals. (5) Does every custom element behave like its native counterpart? Matches against ARIA APG patterns.

4. **Common failures grid** — 6 cards with severity: (Critical) Focus outline removed with no replacement; (Critical) Modal dialog without focus management; (Critical) Missing skip navigation link; (High) Custom interactive elements not in tab order; (High) Hover-only menus; (High) Positive tabindex values.

5. **Fix patterns** — 4 working code examples: (1) `:focus-visible` to restore focus indicators without regressing mouse UX; (2) skip navigation link (visually hidden, shown on focus); (3) FocusTrap class for modal dialogs (open with trigger reference, Tab cycle containment, Escape to close, return focus on close); (4) native `<button>` vs. div-as-button with required ARIA + keyboard handler.

6. **Automated tools** — manual keyboard-only test, Axe DevTools extension, ShipSafe, axe-core CLI for CI (`npx axe-core-cli`). Honest callout: automated tools detect ~30-40% of real issues; manual testing is required.

7. **Verify with ShipSafe** + CTA.

8. **FAQ** — 7 questions: WCAG criteria, keys to use, keyboard trap definition, tabindex usage, accessible modal pattern, why custom dropdowns fail keyboard, ShipSafe keyboard coverage.

### Guide content summary

**JSON-LD:** TechArticle with nested FAQPage (7 Q&As), datePublished/dateModified 2026-10-17

6. **Prevention checklist** — 5-step list: audit prefixed vars, LeakCheck .env before committing, disable source maps in production (`build.sourcemap: false` / `devtool: false` / `productionBrowserSourceMaps: false`), write server routes for secret-bearing APIs, ExposureCheck after config changes.
