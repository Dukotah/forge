### Why this guide / why now

The 2026-09-29 and 2026-09-25 ops-log entries both named "HardenCheck ninth guide — CORS misconfiguration" as the top Task (a) candidate. HardenCheck had 8 guides covering CSP, HSTS, X-Frame-Options, X-Content-Type-Options, CSP strict-dynamic, CSP for React/SPA, Referrer-Policy, and Permissions-Policy. None covered CORS. The CORS misconfiguration cluster ("cors misconfiguration security", "fix access-control-allow-origin", "cors header security best practices", "wildcard cors with credentials") is high-volume and targets developers who either see CORS flagged in a security scan or are implementing CORS for the first time and making common mistakes.

**Why it opens a new cluster:**

All 8 existing HardenCheck guides cover HTTP response headers that control browser behavior (CSP, HSTS, XFO, XCTO, Referrer-Policy, Permissions-Policy). CORS is a distinct topic: while CORS headers are HTTP response headers that HardenCheck reads, the security concern is configuration logic rather than presence/absence of a header. The guide targets the developer evaluating their `Access-Control-Allow-Origin` policy — a different moment and intent from "my scanner said I'm missing a header."

**Why CORS fits HardenCheck specifically:**

HardenCheck reads response headers and flags `Access-Control-Allow-Origin: *` as a finding. The guide is the natural destination when a developer sees that flag and wants to understand when wildcard is safe vs. dangerous, and how to implement a correct origin allowlist.

### Guide content summary

**JSON-LD:** TechArticle with nested FAQPage (7 questions) as mainEntity, datePublished/dateModified 2026-10-01

**Sections:**

1. **How CORS works** — same-origin policy overview, what CORS headers do, browser enforcement vs. server-side clients. Callout clarifying CORS is entirely browser-enforced (server-side clients ignore it).

2. **The five dangerous patterns** — styled misconfig-card blocks, each with a risk badge:
   - **Critical**: Reflecting the Origin header unconditionally with `Access-Control-Allow-Credentials: true` — the canonical CORS vulnerability; every origin is trusted
   - **High**: Substring/regex matching (`endsWith`, `startsWith`, `includes`) instead of exact equality — all three common patterns with their specific bypass attacks
   - **High**: Allowing the `null` origin — sandbox iframe exploit with code example showing how it works
   - **Medium**: Missing `Vary: Origin` on dynamic CORS responses — cache poisoning risk
   - **Medium**: Overly permissive preflight (`Access-Control-Allow-Methods: *`, `Access-Control-Allow-Headers: *`)

3. **When wildcard is safe** — comparison table (CDN static assets, public read-only API vs. authenticated APIs, internal APIs) with Safe/Caution/Never badges. Callout clarifying that browsers refuse `*` with `credentials: true` — the reflected-origin pattern is the real threat.

4. **Correct allowlist implementation** — Node.js/Express (Set-based equality check with Vary header), Python/Flask, Python/Django (django-cors-headers config note).

5. **Deploy on your platform** — nginx (map block for dynamic allow-origin), Apache (.htaccess with anchored regex), Vercel (static single-origin vs. API function for multi-origin), Next.js (headers config + middleware note), Netlify (_headers for single-origin + Edge Function note).

6. **Verify with HardenCheck** — how to capture API response headers with curl for the specific test origin; what HardenCheck flags.

7. **FAQ** — 7 questions: is wildcard always a risk, what is reflected origin, can I use regex matching, what is the null origin, what is Vary:Origin, does HardenCheck check CORS, does CORS header bypass same-origin policy.

All content technically accurate. No fabricated metrics.
