**Why this topic / why high-intent:**
Hundreds of thousands of businesses pay $50–$500/month for accessibility overlay products (accessiBe, UserWay, AudioEye, EqualWeb) expecting legal protection from ADA website lawsuits. The reality — that overlays do not reliably prevent lawsuits and that courts evaluate actual WCAG 2.1 AA conformance via real AT testing, not widget presence — is underserved as an SEO article. ShipSafe's last guide shipped on 2026-07-31 (the ADA demand letter response guide), making it the most overdue tool for a new guide in the suite.

**Article structure (~1,000 words):**

1. **The short answer box** — overlays don't reliably prevent lawsuits; courts evaluate actual accessibility, not product subscriptions. No overlay vendor certificate has legal weight.
2. **What overlays actually do** — technical explainer: JS widget, runs after page load, injects ARIA, adjusts contrast at render time, provides a preference toolbar.
3. **Why they don't provide legal protection** — ADA Title III standard is actual user access; courts use expert witness AT testing + plaintiff testimony; the National Federation of the Blind and hundreds of accessibility professionals have formally opposed overlay products as harmful to screen reader users.
4. **What overlays cannot fix** (two-column table): can't fix → missing alt text, unlabeled form inputs, broken keyboard nav in custom JS components, focus trap bugs, heading hierarchy, ARIA roles. May help with → visual preference controls (font size, line spacing) for sighted users with low vision.
5. **The compliance certificate problem** — vendor certificates carry no legal standing; displaying an inaccurate badge may be an aggravating factor; courts measure WCAG 2.1 AA via expert testing.
6. **What actually reduces risk** — checklist: code-level WCAG remediation, git-documented fixes, keyboard testing, accessibility statement, quarterly audits.
7. **If you already have one installed** — don't remove immediately; audit independently, fix in code, test with VoiceOver/NVDA for conflicts.
8. **ShipSafe CTA** — scans live HTML the way automated plaintiff scanners do, with or without overlay running.
9. **FAQ** — 8 questions with JSON-LD FAQPage schema.
10. **Suite cross-links** — ComplyKit, HardenCheck, LeakCheck, ExposureCheck.

Git commit: `53e086c` pushed to `dukotah/depcheck` main

A ~900-word guide targeting the queries **"npm license compliance"**, **"check npm package licenses"**, **"AGPL npm package commercial"**, **"open source license checker npm"**, **"GPL npm project"**, **"npm license check"** — aimed at a developer or engineering manager who has seen the words "AGPL" or "copyleft" in a scan result and needs a concrete answer to "does this actually affect my project?"

**Eyebrow:** "License compliance guide" — fourth distinct guide category alongside Fix (CVE remediation), Audit (pre-deploy security sweep), and Typosquatting (supply-chain attack detection). License compliance is categorically different from all three: it is not a security vulnerability, it is a legal obligation — and `npm audit` has no knowledge of it at all.

**Audience distinction:** The three existing DepCheck guides all target "security vulnerability" searches (CVE, exploit, malicious code). The license compliance guide opens a new, non-overlapping search cluster: engineering managers, startup founders, and developers doing compliance due diligence — people searching because they found "copyleft" in a scan result, are undergoing M&A due diligence, or need to answer a customer security questionnaire. This is a new audience the other guides don't reach.

**Article structure (TechArticle + FAQPage JSON-LD):**

1. **Why license compliance is a separate audit from CVE scanning** — explains the fundamental difference: a CVE is a bug (someone publishes a patch, you upgrade, risk closes); a license is a permanent legal condition. No advisory database tracks it. No future release fixes it. The consequence is a legal obligation, not a vulnerability score.

2. **The npm license landscape** — a table covering nine license types across four columns (license name, type, commercial use safety, key obligation):
   - Safe/permissive: MIT, ISC, BSD-2, BSD-3; Apache-2.0 (with patent grant note); CC0/Unlicense
   - Use with care: LGPL-2.1/3.0 (dynamic linking caveat + JavaScript bundler grey area)
   - Risky: GPL-2.0/3.0 (distribution trigger); AGPL-3.0 (network-use trigger — the web app problem); SSPL-1.0 (non-OSI, full infrastructure requirement); EUPL-1.2 (EU copyleft)
   - No rights: Unlicensed / no license field (legally "all rights reserved")

3. **The AGPL blind spot — especially for AI/ML projects** — the key distinction between GPL (triggered by distribution) and AGPL (triggered by network service). The AGPL paragraph: "for a web app — including APIs, SaaS dashboards, and any backend service with external users — AGPL means: if you use even one AGPL-licensed npm package, you must make your entire application's source code available to users under the AGPL license." Explicit callout box warning about AI/ML libraries: many HuggingFace, model-serving, and LLM client libraries in the npm ecosystem carry AGPL. M&A due-diligence angle: AGPL in a target company's dependency tree is a common deal complication.

4. **How to check all your npm package licenses** — three graduated methods:
   - Step 1: Quick sweep of direct dependencies via DepCheck paste (the no-install path, runs in browser)
   - Step 2: Single-package spot-check with `npm info package-name license` and `npm pack package-name` + reading the LICENSE file in the tarball (plus the caveat: the `license` field is self-reported and can be wrong)
   - Step 3: Full transitive audit with `license-checker --production` — walk the entire `node_modules` tree, JSON output, `--onlyAllow` flag for CI gating

5. **Transitive dependencies: the hidden problem** — explains the mechanism with a concrete scenario (an MIT-licensed utility package adds a feature in a minor release that depends on an AGPL library; your lockfile updates, AGPL enters your production bundle without any change to your own `package.json`). Tip callout: commit `package-lock.json` and run `license-checker --production` in CI on every PR as a build gate.

6. **What to do when you find a risky license** — four options in order of preference:
   - Find a permissively-licensed alternative (search npmjs.com, check download count and maintenance health)
   - Buy a commercial license (the dual-licensing model; common in infrastructure and AI tooling)
   - Isolate via a service boundary (the microservice escape hatch; legally uncertain, treat as last resort)
   - Open-source under the copyleft license (for internal tools, dev tooling, or projects where code is not a competitive secret)
   - Unlicensed packages: contact the author and ask for a license (most will add MIT if asked)

7. **FAQ (7 questions):** Does npm audit check licenses? What's the difference between AGPL and GPL for a web app? Does bundling LGPL with webpack trigger copyleft? Can I use AGPL for an internal tool? What does "SEE LICENSE IN LICENSE.md" mean? Is no-license-field safe? How do I check transitive licenses?
